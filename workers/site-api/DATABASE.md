# DB定義とマイグレーション

DBの構造変更は `migrations/*.sql` を基準にする。`src/schema.ts` は同じ構造をDrizzleから利用するための定義であり、別の初期化SQLは持たない。変更時はSQL・Drizzle・制約テストを同じ変更に含める。

## 新規のローカルDB

`workers/site-api` で実行する。

```sh
bun run db:migrate:local
```

このコマンドは `--local` を固定している。既存の開発DBに手動適用済みのSQLがある場合は、先に下の「既存DB」を確認する。使い捨て環境を作るなら `--persist-to` で別の保存先を指定できる。

履歴は次の順で適用される。

- `0000_create_posts.sql`: 写真テーブル・外部キー・UNIQUE・インデックス。旧 `schema.sql` の初期定義を移したもの。
- `0001_add_books.sql`: 読書テーブル。
- `0002_seed_books.sql` / `0003_set_cover_urls.sql`: 過去の読書データ移入。適用済み履歴を変えないため、そのまま保存している。
- `0004_add_face_out.sql`: 過去に追加した未使用列。削除せずDrizzleにも定義する。
- `0005_add_post_deletions.sql`: 投稿削除後も画像キーを保持する削除作業記録。投稿への外部キーは設けない。
- `0006_add_post_upload_state.sql`: 公開状態・アップロード識別子・保存予定キー。既存投稿はpublished、識別子なし、予定キーなしとして保持する。

新規DBには歴史的な読書データも入る。今後の検証データはmigrationへ追加せず、fixtureや開発用seedに分離する。`seed-dev.sql` は写真の検証データ用であり、対応するR2オブジェクトは別途必要。

## テストDB

Vitest設定で `readD1Migrations()` を使い、共通の `test/setup.ts` が `applyD1Migrations()` で同じSQLを適用する。その後、テーブル構造と適用履歴を残してデータを空にし、各テストが検証データを用意する。テストごとのストレージ分離は既存のWorkersテスト環境を使う。

`test/migrations.spec.ts` は日時既定値、外部キー、UNIQUE、削除連動、列とインデックスの整合を検証する。また、0003まで適用したDBのデータを編集し、0004以降の適用後に値が保持され、新規DBと同じ構造になること、履歴付き再適用で変化しないことを確認する。

## 開発DBのリセット

旧 `schema.sql` は削除した。`reset-dev.sql` はテーブルと適用履歴を削除する処理だけを持ち、初期化DDLは複製しない。保存データを破棄してよいローカル環境に限り、次を実行する。

```sh
bunx wrangler d1 execute DB --local --file=reset-dev.sql
bun run db:migrate:local
```

別の `--persist-to` を使う場合は両コマンドに同じ保存先を指定する。本番・保存が必要なDBには使わない。

## 既存DBの適用履歴

過去のSQLは `wrangler d1 execute --file=...` で手動実行する運用だった。この方法では、実際に適用されていても `d1_migrations` に履歴がない場合がある。テーブルが存在するだけでは、migration runnerへ移行できたことにはならない。

既存DBへ一括適用する前に、次を読み取りで照合する。

1. `sqlite_master`、`PRAGMA table_info`、`foreign_key_list`、`index_list` で構造を確認する。
2. `d1_migrations` の有無と適用記録を確認する。
3. 0002/0003によるデータ投入履歴と `books.face_out` の有無を確認する。
4. 実構造と履歴を突き合わせ、適用済み履歴の登録・未適用SQLの実行手順を個別に決める。

履歴なしのDBへ一括適用すると、読書データの重複、表紙URLの上書き、既存列の追加エラーが起き得る。0000の `IF NOT EXISTS` も既存テーブルの制約不足を修復するものではない。今回のテストは履歴を管理したDBの移行を確認しており、実本番DBの構造・適用履歴は未確認。本番へのSQL実行や自動migrationは追加していない。

Drizzleの日時既定値をSQL式に直した変更は今後のINSERTに作用する。過去に保存された文字列 `CURRENT_TIMESTAMP` は自動修復しない。また、Drizzleが参照する `face_out` が対象DBに存在することをデプロイ前に確認する。

## 削除処理のデプロイ前確認

現行コードの公開・保存・削除・管理画面には0005・0006が必要。コードのデプロイ前に適用する。既存の0000〜0004の履歴を確認せず、一括再適用しない。今回、実本番DBへのSQL実行は行っていない。

投稿削除時に画像キーの記録と投稿行の削除を同じトランザクションで行う。R2の画像を削除し終わってから記録を消すため、途中で通信が失敗しても再実行できる。`post_deletions` を手動削除すると未削除画像の追跡を失うので、通常は管理画面の再試行ボタンから処理する。

保存失敗時の後片付けも同じ記録を使う。投稿行の削除と画像キーの記録がコミットできた場合、以降のR2障害や完了記録の削除失敗は管理画面から再試行可能。既存記録にキーを追加するときは統合し、完了時は読み取り時のキー集合と一致する記録だけを削除する。

新規投稿はpendingで作り、R2書き込み前にupload_keysへ全保存予定キーを記録する。全画像保存後にpublishedへ更新し、識別子と予定キーを空にする。途中終了した投稿は非公開のまま管理画面に残り、画像行がなくても予定キーを使って手動削除できる。アップロードが終了・中断していることを確認してから削除する。稼働中処理との排他や自動回復は未実装。既に配信した画像のCDN・ブラウザキャッシュを即時無効化する変更は含めない。
